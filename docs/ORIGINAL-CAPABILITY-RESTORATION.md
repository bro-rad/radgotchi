# Original capability restoration and hardening

## Scope and conclusion

This is a source audit and implementation roadmap, not a deployment qualification or authorization to enable privileged features. Restore the expressive **RAD TERMINAL** and pet, not a generic infrastructure dashboard. Most original experiences are feasible in a browser; powerful integrations need narrower authority, not permanent exclusion.

This roadmap inventories original source behavior; proposals below are not a
list of shipped capabilities. Current release **0.1.5** has been independently
verified live with original artwork/style, grouped package monitoring, single-owner
token login, persistent original-rule games/shop/progression, local Pomodoro and
optional muted audio. See [current integration](companion-integration.md) and
[production boundaries](../DAPPNODE-INTEGRATION.md). The companion-volume and
single-owner choices are implemented, not pending decisions. Broader needs,
contracts, desktop parity, chat, NATS, mesh and host/resource telemetry remain
partial or deferred. Further work is tracked in [issue #1](https://github.com/bro-rad/radgotchi/issues/1).

The upstream web entry is `chat.html`, served/injected by `src/main/web-server.js`; `index.html` is the Electron pet. Inspect both to recover behavior, but preserve the canonical web layout, original `chat-window.css`, artwork bytes, inversion/glow filters, colors, scanlines, typography, sounds and terse EN/中文 voice. Native controls may need accessibility semantics; they do not need a new design system.

### Classification

- **F — Frontend restoration:** no additional trusted authority required. Local storage is user-editable, non-secret, non-authoritative state. Local fun is real functionality, not fake monitoring or verified scores.
- **B — Scoped backend/auth/data:** feasible after the stated principal, persistence, endpoint, or integration decision and security tests. A local-only F variant can precede shared B state.
- **D — Desktop-only semantics:** cannot faithfully reproduce operating-system-wide behavior in the DAppNode browser. Preserve the desktop edition or offer an explicitly in-page alternative; do not pretend a container is the user's desktop.

“Not yet enabled” is a release gate, not a judgment that a capability must never return. Conversely, shipping an asset or exposing a button is not a working restoration.

## Security findings that affect restoration

These are source observations, not claims of successful exploitation or a completed penetration test.

1. **Generic bridges cross too many boundaries.** Upstream `web-server.js` maps invoke/send channels to chat, configuration, memory, mesh, arcade and XP. Re-enabling `web-bridge.js` wholesale would restore authority alongside UI. Port narrowly owned client controllers; explicitly register each supported operation.
2. **The skill sandbox is not a security boundary.** `skill-loader.js:212–239` supplies `require` and `process` to `vm.Script`. Its `Promise.race` deadline at lines 339–347 does not terminate executing work. A dangerous-flag filter is useful UI policy, not isolation or least privilege. Killable separated workers and typed adapters are prerequisites for network-facing execution.
3. **Global process state is not multi-user storage.** XP, needs, arcade round and shared broadcast/persistence modules were built around one companion. Two browser logins must not silently share memory, balance, active blackjack or messages. Choose shared household pet deliberately, or refactor state by principal; even a shared pet does not imply shared private chats.
4. **Manifest and profile projection need redesign.** Upstream `serveManifest` places an authenticated token in `start_url`; do not copy this behavior. `serveChatHtml` injects serialized state/profiles into inline script. Replace with explicit non-secret DTOs and safe serialization/API loading; hostile names must not close a script tag. The broader upstream CSP allows inline code and broad remote connections/images; retain the successor's restrictive policy and add only narrowly required directives.
5. **Attachment limits must agree end-to-end.** `messages.js` has a per-file 20 MiB client cap while upstream `web-server.js` caps JSON bodies at 16 MiB; encoding and multiple files worsen the mismatch. A new protocol needs a single documented aggregate budget, streaming limits, decoded-size checks and clear errors. Provider support must be tested rather than inferred from the file picker.
6. **Legacy mesh identity is not authenticated.** `rad-mesh.js` parses protocol/node IDs and deduplicates message IDs, but those checks are not a signature or authorization. Presence includes hostname and receives network addresses. Retain validation, add resource limits and authenticated identity before trusted cross-node actions; keep legacy displays visibly unverified.
7. **Container telemetry is not desktop telemetry.** `system-monitor.js` uses `os` and platform-specific `exec` probes. Neither porting those calls nor substituting browser estimates supplies verified DAppNode CPU, process health or internet status.

## Keep observation, pet, identity and integration state separate

Suggested contracts are design proposals, not existing APIs:

- **Observation projection:** source/scope, observed-at, last-success, freshness/status, grouped package facts, optional named metric samples with units. Read-only, bounded and sanitized; unknown health remains unknown. Package groups are not individual containers; do not derive identity from IP or array index.
- **Pet state:** version, owner/guest scope, needs, morale/archetype, XP/rank, inventory, timer, contracts, activity statistics. No field can change observed health. A shared ledger's accepted event is not proof a human actually worked or paid attention.
- **Presentation preferences:** language/theme/zoom/motion/audio/panel state; no credentials, role assignments or endpoint URLs.
- **Private conversation state:** owner-scoped histories, attachments and memory with independent retention/export/delete. Model outputs cannot mutate monitoring facts or acquire new permissions.
- **Integration configuration:** operator-owned endpoint IDs, secret references, egress scopes, allowed tool/action IDs. Browser sees capabilities and redacted metadata, not secrets or host paths.

Expression arbitration should be a small pure function: authorization/error/stale/unconfigured observation state remains visible above selected-package evidence; normal pet sleep, care, work, attention and game celebrations can play only without concealing that status. A separate permanent observation indicator permits more expressive play safely. Timer completion, sleep, offline mode or a high pet rank must never imply infrastructure recovery.

## Decisions for further shared/backend restoration

| Decision | Suggested bounded default; owner choice still required |
|---|---|
| Who owns the pet and data? | Current production uses one owner across token sessions and a persistent companion volume. Separate accounts, guests, migration and cross-device merge beyond this shared owner remain future decisions. |
| What does login authorize? | Separate viewer, pet participant, chat user and integration operator scopes. Game clearance does not grant roles. Define session expiry/revocation, reauthentication and principal identifiers before shared services. |
| Where does progression live? | For shared game telemetry, extend existing Hasterrad API/auth/score persistence where approved rather than inventing a competing backend. Decide ownership and availability explicitly; broker failure must not break scores. Browser reports remain unverified activity unless backed by server-owned game transitions. |
| Which LLM, network and credentials? | Choose endpoint location/reachability, provider/model capabilities, egress destinations, credential owner/storage/rotation, per-user quotas, and whether cloud calls are allowed. Do not probe or configure these during this audit. |
| What may leave the node/browser? | Decide prompt/attachment/telemetry disclosure, memory extraction, external search, provider retention and proactive calls. Default to minimal explicit context; never include secrets or inventory wholesale. |
| Which monitoring resources? | Identify approved read-only CPU/RAM/network/application-health source, unit/scope semantics, sampling budget, access and retention. Until then show unavailable, not zero. |
| Which mesh trust model? | Choose authenticated broker/pairing or isolated unverified legacy LAN gateway, opt-in advertised fields and whether messaging is allowed. No host networking or port exposure as an incidental UI restoration. |
| Which tool operations? | Decide approved adapters, workspace roots, egress rules, approval ownership, audit retention and killable runner architecture. Any control-plane mutation is a separate explicit project authorization. |
| What are game/time rules? | Decide offline decay, timezone/day rollover, passive XP, away caps, spendable-XP rank behavior, abandoned rounds, practice vs verified score semantics, and migration from old single-user files. |
| PWA/privacy policy? | Token-free install, no private cache by default, offline-only label, login in separate cookie jars, and user-controlled removal of local pet/chat data. Never promise reliable browser background timers or capture support. |

## Roadmap and acceptance gates beyond the current baseline

### Phase 1 — Recover original fun without new authority

Restore original local preferences, art/idle/touch reactions, sleep, synthetic audio, localized terse labels and bounded in-page movement. Support a genuine local pet/practice mode if chosen, with explicit non-shared state. Preserve monitoring expression priority. Preserve the integrated interaction, Pomodoro, login/auth and freshness/focus/mobile behavior. A new mini-game is additive; it does not complete coinflip/blackjack/shop restoration.

Acceptance: real browser at desktop and phone widths; all original restored controls operate by keyboard/touch; original sprite bytes decode with original glow; contrast and focus visible; reduced-motion/mute honored; hidden-tab timers/listeners cleaned up; storage unavailable/corrupt/version-upgrade cases safe. Exercise waiting, unauthorized, unconfigured, connected, stale, failed and recovery observations while petting/sleeping/playing. No pet action opens privileged routes or alters monitoring truth.

### Phase 2 — Durable pet, ranks, shop and original arcade

Single-owner persistence, pure original-rule core, typed actions, atomic snapshots, inventory and both original games are integrated. Broader needs lifecycle, attention, morale/archetype, milestones/streaks and daily-contract rewards still require explicit rules and qualification. Separate practice or multi-user modes are not implied.

Acceptance: another principal cannot read/mutate state; guest migration explicit; no arbitrary XP/price/effect submitted by clients; integer and range validation rejects NaN/infinite/negative/oversize inputs; duplicate/out-of-order requests and concurrent tabs cannot double reward/spend; restart during debit/settlement recovers consistently; server never leaks dealer hidden state; clocks/day rollover/abandoned games deterministic. Verify original thresholds/ranks/catalog against source fixtures. No claim of tamper-proof human attention.

### Phase 3 — Useful resource observations

Connect only approved read-only collectors. Add CPU/RAM/network and application health independently with provenance, freshness, correct units and optional native bar/face reactions.

Acceptance: missing/partial/old/malformed samples render unknown/stale; container vs host vs browser scopes cannot be confused; grouped packages remain grouped; source credentials/IPs are not exposed; backend timeout/redirect/body-size and caching bounds tested; feed outage does not destroy pet saves and pet service failure does not block observations.

### Phase 4 — Chat, attachments and memory

Choose provider/principals/secrets policy; restore bounded tool-free streaming chat first, then validated attachments and opt-in memory/proactive behavior. Reuse the original transcript, thinking/upload faces, latency sparkline and profile selector.

Acceptance: server-side allowlisted endpoint cannot be replaced by browser input; redirect/DNS destination changes tested against policy; no credential in HTML/manifests/URLs/errors/logs/storage; cross-user stream/history/memory isolation; malicious Markdown, inline-script terminators, attachment polyglots/oversized dimensions and prompt injection remain inert. Cancel/timeout aborts upstream work; slow clients and concurrent sessions bounded; clear/export/delete covers retained attachments and summaries; disabled capabilities have honest labels. Real selected-provider smoke test is a later authorized gate, not satisfied by fixtures.

### Phase 5 — Optional mesh and approved tools

Add read-only mesh/gateway projection and reviewed skill catalog, then permissioned messaging and typed integrations. Put command/document processing in a separately reviewed constrained runner if approved. Keep integrations independent of core monitoring/game operation.

Acceptance: unauthenticated/spoofed/replayed/flooded peers cannot claim trusted identities or trigger execution; per-peer/global caps and expiry enforced; HTML injection inert; publish permission separate from view. Tool argument/path/symlink/egress/secret-exfiltration tests pass; approvals bind exact action and principal; deadline actually kills work; no Docker socket, host filesystem, privileged container or DAppNode admin access. Home Assistant writes and any other effect require their own approved scopes.

### Phase 6 — Installable polish and release qualification

Restore manifest/icons and supported standalone behavior with token-free login. Optional offline shell caches public static files only; never synthesize live data. Re-run combined packaging and browser qualification after all concurrent changes land.

Acceptance: exact static allowlist, Docker COPY and Dockerfile context allowlist include every restored dependency and exclude source/secret/skill leakage. Strict CSP remains effective without broad `unsafe-inline` or arbitrary network origins. Test session expiration/logout, CSRF, cross-origin fetch/WebSocket and native login form submission; no null-Origin blanket exception. Installed-app cookie isolation yields normal login. Offline/online transitions never show old metrics as live. Frozen-image/build/native-install/public verification are separate authorized work, not part of this document.

## Audit completion and limitations

Inspected the original web/desktop markup, settings and bridges, renderer mood/interaction/audio modules, chat/attachment modules, bootstrap/persistence, needs/XP/contracts/arcade/focus/sleep, LLM/memory/skills, mesh/discovery, system probes, and the successor monitoring shell/routes. The baseline is the local upstream ref, not a claim about the latest remote revision. This is a capability and threat-boundary inventory, not exhaustive exploit validation. Proposed gates have not been executed by this documentation-only task; concurrent implementation and deployed behavior must be qualified separately. No original capability is rejected merely for being powerful: F capabilities have an immediate route, B capabilities have scoped prerequisites, and D limitations are accompanied by honest browser alternatives or a separate desktop path.
